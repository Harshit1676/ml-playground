# Proposed experiment admission policy

One active experiment with zero queue is approved for a controlled single-process staging trial. One Uvicorn worker can handle concurrent requests, so this trial requires an explicit admission gate. Its implementation is pending. An upstream timeout must retain the slot until the underlying work finishes.

The shared rates of one request per second globally and six requests per minute per client are unapproved hypotheses. The proposed 256 MiB tier needs measurement on the target platform before approval. Multiworker and multiinstance deployments require separate global enforcement. M6A measured local process CPU, request latency and working set.

| Owner | Proposed staging configuration | Reason |
|---|---|---|
| Python process | Start one Uvicorn worker with one active experiment across the three POST routes and no waiting queue. Acquire immediately before body buffering, after CORS handling. Return a structured 503 with Retry-After of one second when occupied. Hold the slot through actual compute completion and response transmission. Release it on every terminal path, including validation failure and disconnect. | At four simultaneous maximum jobs, Logistic p95 reached 2.82 s and K-Means 3.18 s. A single-job baseline makes contention and recovery measurable. A client abort or proxy timeout alone cannot release capacity while a worker thread is still computing. |
| Shared gateway | Initially allow one sustained experiment per second across the single instance, burst two. Start with six submissions per minute per client IP, burst two, as a fairness hypothesis for manual interaction. Return 429 with Retry-After based on token refill. Accept client address information only from trusted proxies. | Maximum Logistic used about 0.4 CPU seconds per request on the worker. One per second budgets roughly 40% of one core before overhead. The per-client setting needs traffic evidence, especially on shared networks. Point selection and playback do not consume tokens. |
| Hosting platform | Start with one instance, one vCPU and 256 MiB memory. Limit the request body to 1 MiB at ingress as well as in the application. Start with a 10-second total upload deadline and 10-second upstream response deadline. Configure resource, egress and spending alerts. | The worker peaked at 67.64 MiB in the sampled synthetic series. The maximum K-Means in-process measurement reached 75.3 MiB including the client. The memory allowance leaves room for runtime, parsing and serialization. Ten seconds exceeds the measured maximum single K-Means request of 4.62 s. Slow networks, cold starts and actual quotas need a staging trial. |

Keep health and CORS preflight outside experiment admission. Monitor health latency during saturation. Use an asynchronous lightweight health handler if thread-pool contention delays it. Send overload responses with CORS headers and expose Retry-After to browser clients if the UI reads it. Leave retry under user control, with a visible wait and no automatic POST replay.

Each additional worker or instance multiplies local capacity. A process-local gate cannot enforce a shared quota. Enforce aggregate rate and maximum instance count at the gateway/platform. If it lacks a shared concurrent-request limit, bound total active fits by the product of instances, workers and slots. Recalculate before scaling. Prevent direct public access to the origin around gateway controls.

## Controlled acceptance tests

1. On the actual quota, warm each lab and gather 100 maximum serial requests. Use the 101-snapshot K-Means fixture. Record p50/p95/p99/max, CPU seconds, worker RSS, response bytes and status. Compare Linear against its own PRD thresholds.
2. Run same-lab and mixed batches at concurrency 1, 2 and 4. Record active work, queue depth and rejection source. Require at most one fit per worker, zero queued experiments, prompt structured overload responses, and successful recovery on the next available slot. Poll health every second throughout. Start with a staging health p95 budget of 250 ms.
3. Exercise a slow upload, invalid body, interrupted response, and client cancellation during a running fit. Verify the upload deadline, eventual slot release, and that an abandoned fit cannot overlap the next accepted fit. Check Retry-After, cross-origin visibility and recovery.
4. Test per-client fairness and a burst from multiple clients. Repeat with two workers/instances before approving scaling. Verify aggregate quotas still hold, memory stays below budget without restarts, and the configured cost ceiling is observable.
5. Record worker count, hardware, network, power settings and concurrent activity. Test the full-size mobile submission 30 times. Set independent Logistic and K-Means latency objectives before launch.

M6A measured Linear engine p95 at 111.48 ms initially, 370.32 ms during installation and 101.07 ms in its dedicated repeat, all above 100 ms. Mobile maximum submission p95 crossed the 1,000 ms target under contention (1,297.5 ms) and passed on the separate repeat (409.5 ms). The 770 ms and 457 ms four-way Linear results came from different runs. The 67.64 and 75.3 MiB readings cover different processes and fixtures. These measurements support a conservative trial rather than a production capacity guarantee.
